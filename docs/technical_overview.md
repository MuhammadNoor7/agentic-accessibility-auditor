# Accessibility Auditor: Technical Overview

## 1. Project Goal
The goal is to build an **Agentic Accessibility Auditor** capable of analyzing Android applications for accessibility violations (e.g., contrast issues, missing labels, small touch targets). 

Because many Android applications block access to their "Accessibility Tree" (the structured XML view hierarchy), your auditor must be able to perform its task using **raw screenshots** as its primary input.

## 2. Technical Architecture: The Hybrid Pipeline
The auditor uses a two-phase architecture to maintain accuracy and performance:

1.  **Phase 1: Object Detection (The current work)**
    *   **Task:** Detect and locate UI elements in a screenshot.
    *   **Model:** **YOLOv11** (Dynamically configured based on available GPU VRAM).
    *   **Output:** Bounding boxes + Class labels (e.g., "button_labeled", "text").
2.  **Phase 2: Violation Classification (The planned roadmap)**
    *   **Task:** Take the cropped elements found in Phase 1 and classify them as "compliant" or "violating" (e.g., "contrast check passed" vs. "contrast check failed").
    *   **Model:** **MobileNetV3 or EfficientNet-B0** (CNN classifiers).

---

## 3. Implementation: `train_yolo_ui_detector.ipynb`

### Data Preprocessing
The notebook does not simply "train on images." It performs a sophisticated **XML-to-YOLO conversion**:
*   **Input Data:** Raw Android UIAutomator XML dumps and corresponding screenshots (`data/data-masc`).
*   **Label Generation:** It uses your existing XML parser (`src/parser.py`) to extract component bounds. It then filters out noise (off-screen elements, hidden components, zero-area boxes) to generate clean YOLO-formatted text labels.
*   **Taxonomy (Classes):** It maps Android UI classes to 9 specific accessibility-relevant categories:
    *   `text`, `image`, `icon`, `button_labeled`, `button_icon_only`, `input_field`, `checkbox_toggle`, `tab_item`, `list_item`.

### Training Configuration
*   **Input Size:** `imgsz=960` (High vertical resolution to capture small mobile UI elements).
*   **Augmentation:** Uses standard YOLO mosaic augmentation, but **vertical flip and rotation are explicitly disabled** because mobile UI screenshots are never upside down or tilted.
*   **Dynamic Weight Selection:** The notebook automatically tries to load the `screen2ax` (Large) model for maximum accuracy. If hardware constraints prevent this, it defaults to YOLO11 Medium or Small.

## 4. Understanding your Training Artifacts (`runs/`)

Your `runs/runs/yolo_ui_detector/` folder contains the "paper trail" of your training session. Here is how to interpret the key files found there:

| File / Folder | Description |
| :--- | :--- |
| **`weights/last.pt`** | The state of the model at the very last epoch. Used to resume training if interrupted. |
| **`weights/best.pt`** | The state of the model with the highest validation accuracy achieved during training. **This is the file used for inference.** |
| **`results.csv`** | Contains the epoch-by-epoch metrics (precision, recall, mAP, and loss values). |
| **`training_curves.png`** | A visual summary of the loss and mAP over time. If your loss is still dropping sharply at 60 epochs, you should increase the `epochs` setting. |
| **`confusion_matrix.png`** | Shows how often the model confuses one class for another (e.g., confusing "text" with "button_labeled"). |
| **`val_batchN_pred.jpg`** | Visual samples from the validation set, showing the model's boxes overlaid on real screenshots. **Crucial for sanity-checking your model's quality.** |
